## Grafo e ordem proposta

```text
Base local (20261102 entitlements + schema/RLS/Storage)
  ├─ 01 grupos/lotes ──> 02 gestão de lote/carrossel
  ├─ 03 MIME imagem ─────┐
  └─ 04 quarentena/validação (corte coordenado com 03)
       └─ 05 validação vídeo/legacy/cleanup
            ├─ 06 heartbeat (worker validator compatível)
            ├─ 07 credenciais/nonce (Edge API + worker)
            │    └─ 08 upload confirmado (Edge marker + Storage)
            └─ 09 RPCs protegidas (frontend com request_id; bundle legado fail-closed)
```

O desenho abaixo é somente ordem de dependências estáticas; não recomenda aplicar todas juntas. Em staging, separar lote/DB, pipeline de mídia e RPC de plano/job como releases coordenados. M03 e M04 devem ser ensaiadas como corte de upload contínuo. M06–M08 exigem coordenação banco/Edge/worker. M09 é um rollout separado do frontend/PostgREST. Nenhuma assinatura, cron ou deploy Cloud é autorizado.

## Critérios mínimos antes de qualquer migration

- Reconciliar estado Cloud atual por evidência autorizada; comparar conteúdo/corpos por método seguro, não apenas ledger.
- Calcular/aprovar hash do arquivo exato e dependências; revisar SQL completo.
- Restaurar backup em ambiente isolado e medir migração, locks, WAL, duração e efeitos sobre mídias.
- Testar rollback/restauração com snapshots sintéticos; mudanças de estado/dados não têm down migration simples.
- Garantir versões compatíveis de frontend, Edge, worker e config Storage; observar clients antigos/cache.
- Desligar limpeza física e manter `auto_delete_media_enabled=false`, `dry_run=true` até decisão separada.
- Autorizar cada migration e serviço separadamente. Resultado de teste local não é autorização de implantação.
